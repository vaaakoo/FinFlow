# FinFlow Implementation Guide

FinFlow is a local simulation of GEL banking. The base demo runs the Ledger API and PostgreSQL, with RabbitMQ and Notifications added when needed. Secured mode adds Keycloak, a gateway, the other services, and the Angular portal. The services own separate databases on the local PostgreSQL instance. See the [low-resource handoff](DEVELOPMENT_HANDOFF.md) for copyable test commands and [project status](../PROJECT_STATUS.md) for verified results and open checks.

## Starting points

- [.NET solution](../FinFlow.slnx) lists the ASP.NET Core APIs, notification host, shared libraries, tests, benchmarks, and Aspire AppHost. [Directory.Build.props](../Directory.Build.props) sets the .NET target and [Directory.Packages.props](../Directory.Packages.props) pins NuGet versions.
- Service `Program.cs` files register dependencies, apply EF Core migrations, and map routes. Business rules live with the services that own the data. The code uses separate command and query handlers where useful, with Dapper for ledger statements and reconciliation. The services share contracts and technical infrastructure.
- [Base Compose](../compose.yaml) starts PostgreSQL and the Ledger for `docker compose up -d --build ledger`. [Secured Compose](../compose.secure.yaml) adds the portal and secured workflows. The [Dockerfile](../Dockerfile) builds separate .NET service images. Run one stack at a time.

## Identity and account setup

1. The [Keycloak realm](../infrastructure/keycloak/finflow-realm.json) defines demo users, roles, the public portal client, and confidential service clients. [PortalComponent.ngOnInit and signIn](../frontend/src/portal.component.ts) configure OIDC and start Authorization Code sign-in with PKCE. The callback completes sign-in and the portal uses the access token for API calls.
2. [FinFlowIdentity.AddFinFlowIdentity](../src/FinFlow.Authentication/FinFlowIdentity.cs) sets JWT issuer, audience, discovery, and policies. The [YARP route configuration](../src/FinFlow.Gateway/appsettings.json) maps paths to internal APIs. [Gateway Program.cs](../src/FinFlow.Gateway/Program.cs) applies authorization, rate limits, and correlation. Each destination API validates the bearer token and enforces its own access rules.
3. [CustomerEndpoints.Register and SetStatus](../src/FinFlow.Customers.Api/CustomerEndpoints.cs) register a profile for the authenticated subject and let staff perform simulated KYC. [Accounts.Open and ListOwned](../src/FinFlow.Ledger.Api/Accounts.cs) provision zero-balance accounts and restrict customer lists to the owner. Staff can fund an account from a seeded demo account.
4. [CustomerProfileCache](../src/FinFlow.Customers.Api/CustomerProfileCache.cs) uses Valkey for short-lived own-profile reads. The handler queries PostgreSQL on a cache miss, and writes invalidate the cache. Access and financial decisions use service data and identity policies. A dedicated Valkey outage check is pending.

## Transfers and ledger consistency

1. [TransferEndpoints.Submit](../src/FinFlow.Transfers.Api/TransferEndpoints.cs) inserts an order keyed by customer subject and idempotency key, then returns HTTP 202. A retry with the same input returns the same order. [Get and List](../src/FinFlow.Transfers.Api/TransferEndpoints.cs) give the customer owned status and history.
2. [PostingWorker.DispatchNextOrderAsync and PostOrderAsync](../src/FinFlow.Transfers.Api/PostingWorker.cs) lock a due order with `FOR UPDATE SKIP LOCKED` and make the gRPC call with a service token and the same order ID on each attempt. [ledger.proto](../src/FinFlow.Ledger.Contracts/ledger.proto) defines the internal posting, charge, and refund contracts.
3. [LedgerPostingService.Post](../src/FinFlow.Ledger.Api/LedgerPostingService.cs) calls [Transfers.PostAsync](../src/FinFlow.Ledger.Api/Transfers.cs). PostgreSQL serializes requests for the same scoped key and locks both account rows in ID order. Ledger checks ownership, sufficient funds, and arithmetic bounds. It commits both balances, two signed entries, the posting, and its outbox row together. [LedgerDb](../src/FinFlow.Ledger.Api/LedgerDb.cs) and its [migrations](../src/FinFlow.Ledger.Api/Migrations/) enforce unique posting keys, balanced entries, and immutability. [LedgerQueries.Statement and Reconcile](../src/FinFlow.Ledger.Api/LedgerQueries.cs) use Dapper for paged statements and reconciliation. The base demo calls `Transfers.Create` and posts synchronously.

## Payments and recovery

[PaymentEndpoints.Submit and Refund](../src/FinFlow.Payments.Api/PaymentEndpoints.cs) create a pending payment or request a refund. [PaymentWorker.AdvanceNextAsync and AdvanceAsync](../src/FinFlow.Payments.Api/PaymentWorker.cs) process one locked payment at a time. The workflow charges a protected settlement account, processes the simulated provider result, then settles or compensates. [LedgerPostingService.Charge and Refund](../src/FinFlow.Ledger.Api/LedgerPostingService.cs) post both movements with stable, separately scoped keys. A refund reverses the original amount and uses the original accounts.

- **Polly.** The `PaymentWorker` constructor configures an exponential retry with jitter and a circuit breaker. `CallLedgerAsync` runs token acquisition and the Ledger charge or refund RPC through that pipeline. It applies to selected transient HTTP and gRPC errors. The simulated provider runs inside the durable workflow, which schedules another database-backed attempt on exceptions. The code has both mechanisms. Earlier smoke tests checked uncertain provider recovery and compensation. A targeted demonstration of the Polly breaker opening was not run.
- **Payment event history.** [Payment.MoveTo](../src/FinFlow.Payments.Api/PaymentsDb.cs) updates the operational row and appends a versioned state record plus an outbox event in the same save. `PaymentEndpoints.Get` reads the latest event for the returned status, posting IDs, and reason. The worker and refund decision still read the mutable payment row. This implements versioned history and an event-derived detail view. The roadmap’s limited event sourcing remains partial because the event stream does not drive workflow decisions or rebuild the payment independently.

Use success, decline, or uncertain scenarios in the portal when the secured demo is available. [SimulatedProvider.SettleAsync](../src/FinFlow.Payments.Api/SimulatedProvider.cs) also defines delay, timeout, temporary unavailability, and duplicate receipt cases.

## Messaging notifications and audit

- [OutboxPublisher.PublishBatchAsync](../src/FinFlow.Ledger.Api/OutboxPublisher.cs) publishes Ledger events to RabbitMQ and marks each row published after confirmation. [LifecycleOutbox and LifecyclePublisher](../src/FinFlow.Messaging/LifecycleOutbox.cs) do likewise for Customer, Transfer, and Payment lifecycle events. [RabbitTopology](../src/FinFlow.Messaging/RabbitTopology.cs) defines both routes and the Audit lifecycle quorum queue with bounded redelivery.
- [NotificationConsumer.ConsumeAsync](../src/FinFlow.Notifications.Worker/NotificationConsumer.cs) calls [NotificationsDb.StoreAsync](../src/FinFlow.Notifications.Worker/NotificationsDb.cs). The inbox marker and notification commit together, then the consumer acknowledges. Malformed deliveries are copied to a dead-letter queue and confirmed before the original is acknowledged.
- [NotificationEndpoints.List and MarkRead](../src/FinFlow.Notifications.Worker/NotificationEndpoints.cs) scope history to the authenticated subject. The consumer sends a per-user SignalR update after storage, and [PortalComponent.connectNotifications](../frontend/src/portal.component.ts) receives it. Use history after reconnecting. [NotificationEmailWorker.SendNextAsync](../src/FinFlow.Notifications.Worker/NotificationEmailWorker.cs) sends to a synthetic address through Mailpit and records send status.
- [AuditConsumer.ProcessTransferAsync and ProcessLifecycleAsync](../src/FinFlow.Audit.Api/AuditConsumer.cs) insert minimal records and deduplicate by event ID. [AuditQueries.ListTransfers and ListLifecycle](../src/FinFlow.Audit.Api/AuditQueries.cs) provide staff audit views under the auditor or administrator policy. Audit migrations enforce append-only rows.
